# Платежи — переход с Tribute на ЮKassa

**Дата:** 2026-07-13
**Решение (Эд):** Tribute не даёт продавать подписку через наш Mini App/бот → переходим на **рублёвую кассу ЮKassa** (внешняя платёжная страница + вебхук). Адаптер провайдера делаем сменным (CloudPayments/Prodamus — альтернатива на том же контуре).

## Почему ЮKassa, а не Telegram Stars
Telegram требует продавать цифровые товары внутри бота только за Stars (комиссия ~30%, цена в звёздах). Рублёвую кассу через нативный инвойс для цифровых товаров использовать нельзя — только через внешнюю платёжную страницу + вебхук. Выбран рублёвый путь: реальные рубли, комиссия ~3.5%, но нужна самозанятость/ИП.

## Механика (отличие от Tribute)
Tribute продлевал сам. У ЮKassa автопродление = «сохранённый способ оплаты + автосписания нашим сервером по расписанию»:
1. Первая оплата: создаём платёж (`save_payment_method: true`), пользователь платит на странице ЮKassa → вебхук `payment.succeeded` → открываем доступ + сохраняем `payment_method_id`.
2. Ежемесячно: планировщик находит подписки у которых `expiresAt` близко, списывает по сохранённому `payment_method_id` через API ЮKassa → продлевает; неуспех → grace-период → закрытие.

Для MVP автосписание можно не включать (доступ на 30 дней + напоминание) — код заложен за флагом.

## Что переиспользуется из готового
- Модель доступа `hasAccess`/`Subscription`/`AccessStatus` — без изменений.
- Идемпотентный лог событий (был `TributeEvent`) → обобщаем в `PaymentEvent` с полем `provider`.
- Paywall во фронте (кнопка → внешняя ссылка → поллинг `/access`) — уже есть, меняется только источник ссылки (теперь динамическая от `/api/payments/create`).
- Security-паттерны (единая проверка доступа, premium-видео закрыто на сервере).

## Контракт (новый)
- `POST /api/payments/create` (JWT) → `{ confirmationUrl }` — создаёт платёж ЮKassa на 500 ₽, metadata `telegram_user_id`, `return_url` = Mini App. Фронт открывает `confirmationUrl`.
- `POST /api/payments/yookassa/webhook` (без JWT) — подлинность проверяется **перезапросом платежа через API ЮKassa** (ЮKassa не подписывает вебхуки HMAC; доверяем не телу, а ответу `GET /payments/{id}`), опц. IP-allowlist. `payment.succeeded` → открыть/продлить доступ + сохранить `payment_method_id`. Идемпотентность по id объекта платежа.
- `GET /access` — без изменений.

## Автосписание (recurring)
- На `Subscription` — `paymentMethodId`, `provider`.
- `chargeDueSubscriptions()` — находит истекающие, списывает через API ЮKassa; тесты на успех/неуспех/grace.
- Планировщик (Railway cron) — вызывает раз в сутки; в MVP за флагом `BILLING_AUTOCHARGE_ENABLED`.

## Env (новые)
`YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_RETURN_URL`, опц. `BILLING_AUTOCHARGE_ENABLED`. Не заданы → `/api/payments/*` отвечают 503 (как было с Tribute).

## Что нужно от Кати/Эда (внешний блокер)
1. **Самозанятость или ИП** — без этого ЮKassa договор не оформить.
2. **Аккаунт ЮKassa** → `shopId` + `secretKey` (Настройки → API-ключ), включить уведомления (вебхук) на `https://<api>/api/payments/yookassa/webhook`.
3. Решить: включаем автосписание сразу или стартуем с ручного продления.

## Статус
Tribute-код (webhook/verifySignature/applyEvent) остаётся в репо помеченным deprecated до подтверждения, что ЮKassa-контур рабочий (не удаляем, пока новый не проверен end-to-end). Реальная сверка — на тестовом магазине ЮKassa, когда будет аккаунт.
