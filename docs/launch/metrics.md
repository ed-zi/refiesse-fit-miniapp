# Refiesse Fit — метрики запуска, первая неделя (S4-4)

**Дата:** 2026-07-13
**Владелец:** Growth / Launch Agent
**Связанные документы:** `docs/launch/launch-plan.md`, `docs/product/refiesse-miniapp-mvp-tz.md` (API routes, beta-flow)

> Все целевые значения — **гипотезы для MVP-запуска на один тёплый канал (@refiesse_fit), а не факты и не обязательства.** Даны вилками/целями. Реальный baseline появляется после первой недели; тогда гипотезы становятся ориентирами.
> Источники данных отражают текущее состояние MVP: часть — из логов API / событий, часть — вручную из админки и Tribute. Sentry настраивает DevOps; продуктовой аналитики (Amplitude/GA) в MVP нет (ТЗ раздел 11 — расширенная аналитика вне scope), поэтому первую неделю считаем «полуручным» способом.

---

## 1. Воронка запуска (главное)

Смотрим сквозной путь: открыл → прошёл онбординг → сделал практику → упёрся в paywall → оплатил.

| # | Метрика | Что считаем | Источник (сейчас) | Цель-гипотеза (неделя 1) |
|---|---------|-------------|-------------------|--------------------------|
| 1 | **Открытия Mini App** | уникальные пользователи, открывшие Mini App (первый успешный `/me` / auth по initData) | логи API (запросы `/me`, создание `User`); при настроенном Sentry — событие открытия | 25–40% активных подписчиков канала |
| 2 | **Прохождение онбординга** | доля открывших, сохранивших подбор (`PUT /me/onboarding`) | логи API `/me/onboarding`; в БД — `User.onboarding` заполнен | ≥ 60% от открывших |
| 3 | **Первая тренировка «Я сделала»** | доля открывших с ≥1 `ProgressEntry` | логи API `POST /progress`; в БД — наличие `ProgressEntry` | ≥ 35% от открывших (ключевая метрика ценности) |
| 4 | **Просмотр paywall** | доля открывших, дошедших до Paywall (Locked → Paywall / клик по premium) | логи API (запрос premium `/workouts/:id` без доступа → метаданные; `GET /access`) | 20–40% от открывших |
| 5 | **Клик «Открыть через Tribute»** | переходы на Tribute payment link из paywall | логи API / бот-редирект на payment link (если проксируется); иначе — оценка по paywall-просмотрам | 20–35% от просмотrevших paywall |
| 6 | **Оплаты premium** | подтверждённые `new_subscription` | **Tribute events (админка) + `TributeEvent` / `Subscription` в БД** | 3–7% от открывших (стартовая гипотеза выручки) |

**Ключевые метрики недели (на них смотрим в первую очередь):** #3 (первая практика — реальная ценность) и #6 (оплаты — проверка оффера). Остальное объясняет, где воронка теряет людей.

## 2. Retention (возвращаемость)

Без агрессивного streak — но возвращаемость показывает, живёт ли привычка.

| Метрика | Что считаем | Источник (сейчас) | Цель-гипотеза |
|---------|-------------|-------------------|---------------|
| **Retention D1** | доля открывших в день 0, вернувшихся в Mini App на след. день (auth/любой запрос от того же `telegram_user_id`) | логи API по `telegram_user_id` + дата; ручной подсчёт из БД | 20–35% |
| **Retention D7** | доля открывших в день 0, зашедших на 7-й день | логи API / БД, ручной подсчёт | 10–20% |
| **Повторная практика** | доля сделавших ≥2 `ProgressEntry` в разные дни за неделю | БД `ProgressEntry` group by user/день | 15–30% от сделавших первую |

> D1/D7 в MVP считаются полу-вручную из логов/БД по `telegram_user_id` и датам. Точность приблизительная — это ориентир, не аналитическая система.

## 3. Здоровье оплаты и доступа (техническая надёжность)

Не про рост, а про то, что деньги и доступ работают корректно (критично в первую неделю).

| Метрика | Что считаем | Источник | Норма |
|---------|-------------|----------|-------|
| Успешные webhook `new_subscription` | оплата → доступ открылся автоматически | `TributeEvent` (`signature_ok=true`, `processed_at`) + `Subscription.status=active` | доступ открывается 100% успешных оплат |
| Ошибки/отказы webhook | невалидная подпись (403), необработанные события | `TributeEvent`, логи API, Sentry | ≈ 0 необъяснённых |
| Дубликаты/retry | повторные события не задваивают доступ | `TributeEvent` idempotency по `event_id` | 0 задвоений |
| Отмены | `cancelled_subscription`, доступ не рубится раньше `expires_at` | Tribute events + `Subscription.expires_at` | корректно у 100% |

## 5. Как собираем (процесс первой недели)

Поскольку продуктовой аналитики в MVP нет, сбор — полуручной:

1. **Ежедневно (Growth):** снимок из БД/логов API — открытия, онбординги, `ProgressEntry`, paywall-запросы. Простой SQL/скрипт по датам (запросить у Backend/Tech Lead выборки; НЕ пишем код в этом спринте — только запрос данных).
2. **Оплаты:** сверяем **админку Tribute events** + `Subscription` в БД — число активных подписок, early-bird когорта.
3. **Retention:** раз в день считаем уникальных вернувшихся `telegram_user_id` по логам.
4. **Канал:** статистика Telegram (реакции, просмотры, переходы) — вручную.
5. **Sentry (когда настроит DevOps):** технические ошибки открытия/оплаты — сигнал о сбоях воронки, не бизнес-метрика.
6. **Сводка недели:** таблица «факт vs гипотеза» по разделам 1–2 → выводы и правки оффера/текстов → бэклог спринта 5.

### Зависимости / что нужно
- [ ] Backend/Tech Lead: способ выгрузить события воронки из логов/БД (готовые выборки по датам);
- [ ] DevOps: Sentry настроен, ключевые события открытия/оплаты логируются;
- [ ] Доступ к админке Tribute events (оплаты, отмены);
